# Provisional P0-1 mapping for discussion

Prepared from the maintainer's review and the repository's draft Decision Principles (sections 3-5) and Open Experiments (01-04). No separately identified approved P0-1 protocol was available locally. This is not a protocol approval, task assignment, or implementation plan. The maintainer should confirm the controlling protocol/version before choosing tasks.

| Review area | Current evidence and behavior | Remaining question before implementation |
| --- | --- | --- |
| Current trusted state | runtime.js reviewInput uses fixed objective/context/constraints and a description of validated call arguments. Tools persist state, but account state, consent versions, and execution-time revocation are not attached to Core input. Serialized local calls do not resolve external concurrent writers. | Agree which state is authoritative, how it is versioned, when it is read, and how changes invalidate a decision. |
| Approval followed by fresh review | Every enforced business call receives mandatory review, including after explicit review_action PROCEED and after MODIFY revisions. Regression tests check changed arguments and revised calls. | Explicit model-requested review is not human approval. There is no approval receipt, approver authentication, scope binding, or resume-after-human-approval flow. Define those semantics before testing them. |
| Late or expired responses | Groq requests have an abort timeout; known review errors and unknown/non-PROCEED decisions withhold calls. The exact call is snapshotted. | There is no review deadline, decision TTL, approval expiry, state-version check, or late-review rejection. Groq timeout is not a review-expiry test. Define what cancels a pending action and how stale responses are discarded. |
| Per-category review overhead and completion | Task categories, review events, API usage/timing, waits, statuses, and state/tool scoring are recorded. Aggregate summaries group by condition. Incomplete sessions are kept separately. | No dedicated review-duration metric or per-category overhead report exists. Agree categories, review-time measurement, explicit versus mandatory review counts, denominators, and treatment of waits/errors. Historical event gaps cannot substitute for isolated review latency. |
| Implicit authorization conflicts | Fixtures mainly express explicit prohibitions/consent facts. Across two complete live runs, there were zero prohibited attempts and zero BLOCKs. A scripted comparison-only upgrade remains a Core PROCEED failure. | Discuss cases where capability, requested outcome, ownership, and required consent conflict without an explicit prohibition. Independently label and pair them with legitimate controls before approving a new live pilot. |
| Enforcement and outcomes | Offline enforced calls: four BLOCK denials and one ESCALATE hold; one prohibited upgrade executes after PROCEED. Event/state replay and controls are preserved. | Keep gate compliance separate from decision quality and task outcomes. Do not describe this as general safety, live BLOCK resistance, or full P0-1 validation. |
| Protocol and independent evidence | Maintainer reports independently reproducing the 61 tests and 24 offline sessions on Node 24.22.0. Historical author runs used Node 24.16.0. This packet supports review of historical live records. | Live runs remain author-reported until reviewed. Freeze the next protocol, labels, controls, source/configuration, failure policy, and evidence route before execution. |

Suggested review order: confirm the protocol and evidence route; review these historical artifacts; agree gaps and evaluation criteria; then obtain separate approval for any new pilot, Core pre-check, input-contract change, or implementation tasks. This packet makes none of those changes.
